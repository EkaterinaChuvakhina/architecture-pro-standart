# Architectural Decision Record (ADR)

## Название задачи:
Концептуальная архитектура MVP для открытия депозитов в банке "Стандарт"

## Автор:
Архитектор банка "Стандарт"

## Дата:

## Нефункциональные требования
Опишите здесь нефункциональные требования и архитектурно значимые требования.

| № | Требование                                                                                                                                                                                                                                     |
| :-: |:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1 | Защита чувствительной информации: Шифрование трафика (HTTPS) для передачи данных на сайте и в интернет-банке.                                                                                                                                  |
| 2 | Удобство использования: Интерфейс соответствует корпоративной дизайн-системе (цвета, элементы); быстрый отклик операций в миллисекунды.                                                                                                        |
| 3 | Надёжность: Доступность 24/7 с uptime 99,9%; переключение на резервный ЦОД; избегать перегрузки БД АБС (не использовать прямой API для онлайн-заявок).                                                                                         |
| 4 | Производительность: Отклик в миллисекунды; горизонтальное масштабирование интернет-банка; исправить задержки загрузки справочных данных (>1 сек).                                                                                              |
| 5 | Поддерживаемость: Использовать существующие технологии; экспертиза внутри банка; Kafka для очередей на перспективу; документация для расширения; реализация силами банка (избегать подрядчика).                                                |
| 6 | Ограничения: MVP с обработкой в бэк-офисе (без полной автоматизации); вертикальное масштабирование АБС; несовместимость интернет-банка с Kafka (микросервисы только для депозитов); обязательная идентификация в отделении для новых клиентов. |

Предлагаемые изменения фокусируются на MVP для онлайн-заявок на депозиты, с минимальными вмешательствами в существующие системы (АБС, сайт, интернет-банк). Изменения включают новые микросервисы и интеграции, как показано в диаграмме контейнеров
1. Внедрение новых микросервисов
   Сервис а "Управление депозитами": новый Java Spring Boot сервис с PostgreSQL БД для хранения и расчёта персонализированных ставок для пользователя, хранение заявок на открытие депозита. Интегрируется с новым справочником ставок банка. Реалилизация на Spring бд Postgres, т.к разработчики владеют этими технологиями 
  
2. Сервис "Хранения справочников" в текущей реализации будет хранить актуальные ставки из ЦБ, бд Redis для уменьшения времени ответов  
   
3. Сервис "Контрольных процедур" для синхронизации статуса заявок на открытие депозита, будет вызывать процедуры в бд "АБС" и бд сервиса "Управление депозитами, и отправлять события на обновление статуса, чтобы не изменять код АБС

**Недостатки, ограничения, риски**
1. Использование процедур затрудняет тестирование и отладку, также сильная привязка к определенной бд, при переходе на другую бд будет нужна миграция
2. Разработчикам нужно использовать незнакомую технологию Redis
3. Увеличение числа интеграций, может увеличивать время отклика
4. Усложнение инфраструктурных процессов
